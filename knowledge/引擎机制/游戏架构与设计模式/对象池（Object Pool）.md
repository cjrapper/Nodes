# 对象池（Object Pool）

## 1. 为什么用池（先讲机制）

`Instantiate` 的开销大致来自：prefab 层级反序列化、GameObject 层级克隆、逐个组件的构造与初始化、`Awake` / `OnEnable`；prefab 未加载时还可能触发**同步资源加载**。
`Destroy` 是**帧末延迟执行**的，不是立即释放。

所以池省的是 **创建时刻的 CPU 峰值** —— 这是它的第一受益人，不只是「GC」。

## 2. GC 的模型（本库跨篇最重要的一条）

Unity 用的 GC（Mono / IL2CPP 都是 Boehm）是**保守式、非分代、mark-sweep**，每次都要扫整个堆。所以：

- **分配速率** 决定 GC **多久来一次**；
- **存活对象总量** 决定每次停顿**多长**。

由此修正一个危险结论：**「热路径 new 一个小对象 = 立刻卡」是错的量级判断。**
每秒十几次的小对象分配在 Unity 里通常**完全无感**；真正致命的是**每帧 × 每实体**的分配（1000 个敌人 × 60fps）。

所以「避免分配」必须限定对象：**高频 + 每帧 + 数量随实体数增长** 的那些分配。

{orange|Incremental GC 的引入版本与分帧参数请以官方文档为准，不给版本号。}

## 3. 池不是零成本

池里的空闲对象**仍然可达、仍然计入存活集** → 每次 GC 的扫描基数变大，且**常驻内存上升**（移动端是硬成本）。

- 收益 = 分配速率下降 + 峰值被提前摊掉；
- 代价 = 常驻内存 + 每次 GC 基数变大。

所以必须设 `maxSize`（见 §6）。

## 4. Queue vs Stack：入出都是摊销 O(1)

{red|「因为 FIFO 所以 O(1)」把两个不相关的属性写成了因果。} O(1) 是 `Queue<T>` 和 `Stack<T>` 都有的性质，与 FIFO / LIFO 无关。真正的选型依据是**复用模式**：

| | 好处 | 代价 |
|---|---|---|
| Stack（LIFO） | 刚回收就再取出，**缓存局部性**好（数据还在 CPU cache） | 同一特效可能连续播两次，观感重复 |
| Queue（FIFO） | 轮转周期长 = 天然冷却期 | cache 命中率略差、池内存水位更容易拉高 |

{orange|官方 `UnityEngine.Pool.ObjectPool<T>` 底层用的是 `Stack<T>` —— 按经验记得，但不确定到可以让你背，请去 `UnityEngine.Pool` 源码 / 官方 API 页核对。}
→ 被问「为什么不用 Stack 而用 Queue」，答「按 FIFO 语义更直观 / 有冷却需求」，**不要拿 O(1) 当理由**。

## 5. 生命周期契约（池化最经典的 bug 在这里）

`OnRecycle` 只管回收侧。**取出侧谁保证对象干净？** 速度归零？动画重置？协程停止？事件退订？
→ 定契约：

```csharp
public interface IPoolable
{
    void OnSpawn();     // 取出：重置到初始状态
    void OnDespawn();   // 回收：停协程、退订事件、清引用
}
```

否则就会出「复用的特效带着上一次的速度和缩放出场」。

## 6. 四个真实坑 + 两个代价

1. **只讲扩容、没讲上限**：一次峰值需要 200 个，池就**永久持有 200 个**。
   → 设 `maxSize`，超限时 **`Destroy` 而不是 `Enqueue`**（放弃池化，换内存不涨），或空闲后收缩水位（对应《内存管理》里那个 `Shrink()`）。
2. **重复回收**：同一对象 `Enqueue` 两次 → 之后连续两次 `Dequeue` 拿到**同一引用** → 两个逻辑操作同一对象，表现为「特效莫名闪一下然后消失」。
   → 对象上打 `isInPool` 标记。
3. **池内对象被外部销毁**（场景卸载、别的代码 `Destroy`）→ 队列里留下的是 Unity 的 **fake null**，取出后 `SetActive(true)` 抛 `MissingReferenceException`。
   → **取出时必须判空并跳过**。
4. **热路径上每次 `LogWarning` 是雪上加霜**（字符串格式化，部分平台还会抓调用栈）。
   → 限流：只报一次，或改成计数器。

另外两条代价：

- **`SetActive` 不便宜**：触发整棵子树的 `OnEnable` / `OnDisable` 与组件注册注销；UI 上还会触发 Canvas 重建。这也是「初始化写在 `OnEnable` 里」会和池的复用语义打架的原因。
- **托管 / 原生分层**：`Instantiate` / `Destroy` 动的主要是**原生侧**（加 C# 包装器），它和「避免 GC Alloc」**不是同一件事**。别把两者混成一句说。

## 7. 什么时候**不该**池化

- 创建开销本来就很低；
- 每个实例需要独立的、长时间存在且互不相同的状态；
- 生命周期极长（池化对它的收益接近零，只增加常驻内存）。

没有边界条件的优化规范就是教条 —— 面试官问「什么情况不池化」，答不出来就说明只会喊口号。

## 8. 术语

{red|「饿死 GC 的原理」不是标准术语}，说出来像在复述营销文。
准确说法：**消除稳态期每帧的托管堆分配，把 GC 的触发频率降到接近零**；而且**只对池覆盖到的那部分分配有效**，项目其余部分照样触发 GC。

## 9. 池 × 场景 × 资源卸载

池里的对象持有 prefab / 资源的引用 → **引用计数不归零 → AB 包卸不掉**。
切场景时的顺序要想清楚：先 `Clear()` 池 → 再 `UnloadLevel` / `UnloadUnusedAssets`，否则「池里剩的是 fake null」和「AB 卸不掉」两个 bug 会同时发作。
（与本库《资源加载》的引用计数链路、《内存管理》的 `Clear()` / `Shrink()` 合起来看才算一个知识点。）

## 10. 官方实现与「为什么手写」

Unity 已有官方 `UnityEngine.Pool.ObjectPool<T>`（`Get()` / `Release()`，另有 `PooledObject<T>` 的 `using` 形式）。{orange|引入版本记忆为 2021.1，请去官方 `UnityEngine.Pool` 文档页核对。}

「你手写了对象池」一定会被追问「为什么不用官方的 / 和官方比有什么区别」，要准备答案。{orange|以下为经验判断：官方 `ObjectPool<T>` 是个通用容器（自己提供 create / destroy 回调），并不替你管理 GameObject 的显隐、`IPoolable` 契约、上限与缩容 —— 这些仍要自己写。具体以官方 API 文档为准。}
