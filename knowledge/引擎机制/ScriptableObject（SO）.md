# ScriptableObject：运行时语义与使用边界

（原本写在《对象池》文档里，与对象池零关系，已独立成篇。）

## 1. 它是什么

`ScriptableObject` 继承自 `UnityEngine.Object`（**不是** MonoBehaviour），可序列化成 `.asset` 资源文件，也能被其他 Unity 对象引用。

## 2. 内存模型（原笔记最大的错）

{red|原笔记：「游戏运行后，一万个怪物同时**"读取"**硬盘上的这同一个文件！内存占用极低！」}

**运行时不会读硬盘。** SO 在**加载阶段被反序列化成内存中的一个托管对象**；之后所有引用者指向**同一份内存实例**。磁盘上的 `.asset` 只在加载时读一次。

**「内存占用低」的机制不是「读硬盘」，而是「单一副本被多处引用」** —— N 个引用者共享一份数据，增量内存 O(1) 而非 O(N)。这就是**享元模式（Flyweight）**，顺势把两个知识点接上。

## 3. 修改语义（面试正题，原笔记完全没有）

| 场景 | 行为 |
|---|---|
| Editor 里 Play 模式下改字段 | **会写回磁盘**（污染资源文件、进版本库、同事拉下来是脏数据） |
| 打包后运行时改 | 只影响内存里那一份，**不持久化**，重启即丢 |

**结论：SO 存配置 / 静态数据，不要存运行时状态**（玩家血量、关卡进度、存档）。用 SO 存运行时状态在 Editor 里「看起来能用」，上线才炸。

## 4. 与配置表对比（选型）

| | SO | Excel / CSV → 二进制表 |
|---|---|---|
| 策划改数据 | 需要 Unity 环境 | Excel 就行 |
| diff 可读性 | `.asset` 是 YAML，但 GUID 引用多，diff 难读 | 导出前可读 |
| 运行时内存 | 一个实例被共享 | 取决于加载方式，通常是整批反序列化 |
| 适合 | 少量、结构复杂、需要在 Inspector 里被引用的配置 | 大量数值、策划频繁迭代 |

{orange|以上是经验判断，具体项目差异大；不确定的以你实习项目的实际方案为准。}

## 5. 常见坑

- SO 之间互相引用 → 加载一个会把整条链拖进来（Addressables 下更明显）。
- 只被 SO 引用、没有被任何场景 / Resources 引用的 SO，**可能不会被打进包体**（依赖收集规则），运行时空引用。
- Editor 与 Runtime 行为不一致（见第 3 节）。

{orange|打包依赖收集的具体规则请以你项目使用的 Unity 版本 + Addressables 文档为准，我不给确定结论。}
