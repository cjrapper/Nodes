● 内含碎片： 协程不是多线程，底层是迭代器 (IEnumerator)。
协程：协程的本质，是【C# 语言的迭代器（IEnumerator）机制】与【Unity 引擎主循环（Game Loop）的调度】相结合的产物。
在 C# 里，只要函数返回 IEnumerator，编译器就会把它编译成一个状态机。
里面的每一个 yield return，就像是一把剪刀，把这段代码剪成了一段段的**‘电影胶片’**。
而 Unity 引擎，就是一个**‘电影放映机’**！
当我们 StartCoroutine 时，就是把这卷胶片塞进放映机里。
Unity 引擎在每一帧的生命周期（比如 Update 之后），都会摇一下放映机的摇把——在底层也就是调用一次 C# 迭代器的 MoveNext() 方法！
每次摇把子，代码就往下执行一段，直到遇到下一个 yield return，就停下来等下一帧。
这就解释了为什么协程不是多线程！因为‘放映机’（主线程）自始至终只有一个！它只是在每一帧的间隙，抽空摇了一下胶片而已！
协程是多线程吗？底层的运行机制是什么？
A（底层真相）：
● 绝对不是多线程！ 协程的所有代码都跑在 Unity 的主线程上！
● 底层原理： 协程的本质是 C# 的 迭代器（IEnumerator） + Unity 引擎的 状态机调度。
当你写 yield return null; 时，相当于告诉 Unity 引擎：“我这帧干完了，你先去渲染画面吧，下一帧再来唤醒我往下执行。”Unity 会在每一帧的生命周期里，挨个轮询所有激活的协程，调用它们的 MoveNext() 方法。
💣 面试必考：协程的【GC 性能刺客】
菜鸟写法： 在 while(true) 循环里写 yield return new WaitForSeconds(1f);。
致命后果： 这里的 new 是万恶之源！你每秒钟都在堆内存里实例化了一个全新的 WaitForSeconds 对象！疯狂产生 GC 垃圾！
主程解法（全局缓存）： 在外面先存好 WaitForSeconds wait = new WaitForSeconds(1f);，然后在循环里 yield return wait;。零 GC！

 异步任务（Async/Await）相比协程有什么绝对优势？
A（三大碾压级优势）：
● 能利用多线程（真正不卡主线程）：
如果有一个极度复杂的寻路计算（比如要算 2 秒），放进协程里照样会把主线程卡死 2 秒！但用 Task.Run() 包裹成异步任务，它会被直接扔进**后台线程池（Thread Pool）**里去算，主线程依然保持 60 帧丝滑！
● 天生带返回值：
协程的返回值死死绑定了 IEnumerator，你想从协程里拿个计算结果比登天还难（只能传回调函数 Action）。但异步极其优雅：Task<int> result = await CalculateAsync();，直接拿到结果！
● 完美支持 try-catch 异常捕获：
协程里只要有一行代码报错，整个协程直接静默暴毙，你在外面 try-catch 根本抓不到！而 await 代码可以像普通同步代码一样，被 try-catch 完美包裹，极度安全。
当挂载脚本的 GameObject 被 Destroy 销毁时，它身上的协程和异步任务会发生什么？
A（截然不同的下场）：
● 协程（Coroutine）：随宿主瞬间陪葬！
协程是死死依附于 MonoBehaviour 的。一旦 GameObject 被 SetActive(false) 或者 Destroy，它身上跑的所有协程会被 Unity 引擎立刻强行终止！非常安全，不会有后遗症。
● 异步（Async/Task）：变成无法停止的孤魂野鬼（内存爆炸）！
Task 是 C# 底层机制，根本不归 Unity 引擎管！
如果 UI 面板销毁了，但后台的异步网络请求还在跑。等它 3 秒后跑完，回来试图更新 UI 时，UI 已经死了！瞬间爆出极其致命的 NullReferenceException！
● 主程的破局之法：
使用异步时，必须随身携带 “取消令牌（CancellationToken）”！在 OnDestroy 生命周期里，直接切断令牌，强行终止后台的异步任务。
