 List 是怎么翻倍扩容的？Dictionary 的哈希表原理是什么？
List<T> 的底层是怎么扩容的？为什么说滥用 Add 会导致性能灾难？
A（底层机制 - 翻倍扩容）：
List 底层是一个连续的内存数组 T[]。
● 默认情况下，如果你直接 new List<int>()，它的初始容量（Capacity）是 0。
● 当你第一次 Add 时，它会申请一个长度为 4 的数组。
● 当你加到第 5 个元素时，数组满了！此时它会触发扩容机制（Resize）：
  ○ 申请一块全新的、容量翻倍的连续内存（长度变成 8）。
  ○ 使用 Array.Copy 把老数组的 4 个元素硬拷贝到新数组里。
  ○ 把老数组扔掉（变成垃圾，等待 GC 回收！）。
  ○ 以后每次满了，都是变成 16、32、64、128...
A（面试官必问：怎么优化？）：
永远不要让 List 自动扩容！ 如果你大概知道要装 100 个怪物，必须在初始化时指定容量：List<GameObject> enemies = new List<GameObject>(100);。
这样它上来就直接申请长度 100 的数组，全程 0 次扩容拷贝，0 产生 GC 垃圾
Dictionary 的底层是怎么快速找到数据的？如果发生哈希冲突（碰撞）怎么解决？
A（底层运作流程 - O(1) 的秘密）：
Dictionary 底层其实维护了两个数组：一个是 int[] buckets（抽屉），一个是 Entry[] entries（具体的数据条目）。
当你执行 dic["陈杰"] = 99 时：
● 计算哈希值（GetHashCode）： 系统把字符串 "陈杰" 扔进一个极其复杂的数学公式里，算出一个巨大的整数（比如 2345678）。这就叫 HashCode。
● 取模运算（求余数）： 这个数字太大了，抽屉不够用。系统用这个数字对抽屉的总数量求余数（比如 2345678 % 7 = 3）。
● 存入抽屉： 系统直接空降到 3号抽屉，把 99 塞进去！找的时候也一样，算一下在哪，一秒钟打开抽屉拿出数据。这就是为什么它查找速度是 O(1)！
A（高频考点：哈希冲突 / Hash Collision 怎么解决？）：
假设算出来的余数，恰好也是 3（这就叫冲突了，3号抽屉里已经有东西了）。
C# 底层使用的是拉链法（Chaining）：
3号抽屉不会报错，而是用一根“链条（单向链表）”，把新来的数据挂在老数据的屁股后面。
下次找的时候，打开 3号抽屉，顺着链条往下摸一个就能找到。
A（高阶追问：字典是怎么扩容的？）：翻倍扩容，而 Dictionary 的扩容是找下一个素数（质数）！比如容量从 3 变成 7，再变成 17、37... 为什么用素数？因为用素数去求余数，算出来的结果分布得最均匀，能最大程度减少哈希冲突（防止一个抽屉里挂着几百条数据拖慢速度）！
● Queue<T>（队列）和 Stack<T>（栈）：
它们的底层同样是数组（Array）！只不过队列规定了“先进先出”，它在底层维护了两个指针（头和尾），形成了一个“环形数组”。这就是为什么你拿它做对象池，速度是 O(1)。
● LinkedList<T>（双向链表）：
绝对不要在游戏更新循环（Update）里用它！ 它的每一个节点（Node）都是一个独立的引用类型对象（存在堆里）。你每 Add 一次，就产生一块堆内存，极容易造成内存碎片和毁灭性的 GC 卡顿。只有在频繁需要从“中间”插入或删除数据，且不考虑内存时才用。
ref 和 out 的区别，你把下面这段话甩他脸上：
“它们在底层的物理实现是一样的，本质上都是把变量的内存地址（引用）压入栈中传递，从而避免了值类型传参时昂贵的内存拷贝开销，同时允许在函数内部修改外部的原始变量。
它们唯一的区别是编译器的安全规则不同：
ref 是**‘读写模式’，它假设传入前数据已有意义，所以要求外部必须先初始化；
out 是‘纯写模式’**，它被用来作为额外的返回值通道，外部不需要初始化，但强制要求函数内部必须在 return 之前给它赋值，否则编译器不放行。”
