# AI 写入权限策略（全自动整理知识）

这份文件回答一个问题：**让 AI 自动往笔记库里写东西时，哪些动作可以放开，哪些必须先拦住。**

它是产品决策，不是技术文档。技术实现见 `DESIGN.md`。

> **实现状态（已落地）**：本文档描述的是**当前真实行为**，不是"打算这么做"。
>
> | 能力 | 落地位置 | 回归测试 |
> | --- | --- | --- |
> | 三个可重组工具 | `src/lib/ai/tools.ts` 的 `update_doc` / `rename_doc` / `delete_doc` | `tools.test.ts` 断言它们在清单里，且各自登记了撤销材料 |
> | 改写不丢内容 | `findLostBlocks` 守卫：既有块文字必须原样出现在新内容里 | `undo.test.ts` 断言丢内容时**被拒绝且文档一字未变** |
> | 删除可恢复 | `doc.deleted_at` 软删 + `restoreDoc` | `soft-delete.test.ts`、`tools.test.ts` |
> | 模块保护 | `delete_doc` 对含子文档的模块返回 `isError` | `tools.test.ts` 断言拒绝后**什么都没动** |
> | 撤销 | `src/lib/ai/undo.ts` + `POST /api/tool-calls` | `undo.test.ts` 全量（含三种新工具各自的撤销） |
> | 每笔写入落审计 | `tool_call` 表，含失败的与动手前的快照 | `tool-loop.test.ts` |

## 一、这份策略改过一次，先说来龙去脉

### 旧策略：AI 只能追加

最初的红线是**三条硬约束**：

1. AI 永远不能删（工具清单里**不存在**删除工具）；
2. AI 不能改人写的块（只有 `append_blocks`）；
3. 每笔写入落审计。

理由在当时是成立的：`deleteDoc` 是硬删（`DELETE FROM doc` + 级联删块），
一次误调用永久带走一篇文档；改写会覆盖用户写下的字节。

### 为什么放开了

**用户的原话：「只能追加，不能删除、改名、移动这个设定是不符合的。」**

他的理由比"我想要更多功能"深一层：这个软件的定位是**导师和助手**，
而只能追加的助手**当不了导师** —— 它没法说

- "这两篇内容重了，该合并"（要改写）
- "这块放错分类了"（要移动）
- "这个标题起得不准"（要改名）
- "这条过时了，删掉吧"（要删除）

只能往已有内容的**后面贴补丁**。对一个用来**补视野盲区**的学习工具来说，
这个代价比"可逆的改动"大得多。

### 放开的前提：旧理由已经消失了

判据从"**不做危险动作**"换成"**每个动作都可撤销**"：

| 当年 | 现在 |
| --- | --- |
| `deleteDoc` 硬删，删了就没了 | 软删 + `restoreDoc`，整棵子树可恢复 |
| 改写会覆盖用户字节 | 快照重放 + **按原 id 复活被删的块**（见底线 1） |
| 没有撤销机制 | 快照重放 + 元数据快照，`undo.test.ts` 逐个工具验证 |

**可逆性早就做到了，红线却没跟着放开** —— 那才是真正的不一致。

### 这份策略改过两轮，别只看结论

| 轮次 | 用户的要求 | 改了什么 |
| --- | --- | --- |
| 第一轮 | 「只能追加，不能删除、改名、移动这个设定是不符合的」 | 放开 `rename_doc` / `delete_doc` / `update_doc` |
| 第二轮 | 「**原文可以删，或者说是覆盖**」—— 那条"一字不丢"的规则不对 | 撤掉 `update_doc` 的丢内容守卫，改用它下面的**复原通道**兜底 |

第二轮值得单独说：第一轮放开之后，`update_doc` 仍带着一道
"每个既有块的文字必须原样出现在新内容里，否则整次拒绝"的守卫。
那条守卫**看起来是安全网，实际是半开的门** —— 它把 AI 变成了
"只能加不能减"的助手，而减恰恰是整理的一半。
用户第二次反馈时点破了这件事，于是它被换成了真正的东西：
**不是禁止删，而是删了能原样退回**（详见底线 1 的复原通道）。

> 教训：用"禁止某个动作"来做安全，往往会连带禁掉一半的正当用法，
> 而且被禁掉的那部分**不会有人来报告**（用户只会觉得"这功能不好用"）。
> 更好的做法是让动作可逆，然后允许它发生。

## 二、现在的工具集

九条工具：**3 读 + 6 写**。

### 读（无风险，且是"有针对性帮助"的前提）

| 工具 | 作用 |
| --- | --- |
| `list_docs` | 列出全部文档与模块（含层级、id、类型） |
| `read_doc` | 读一篇的完整正文 |
| `search_blocks` | 按关键词搜知识块 |

`list_docs` 是**第一个**该给模型的工具：没有它，模型只会凭空建议
"你应该补一篇关于 X 的笔记"，而不知道你已经写了一篇。

### 写（全部可撤销）

| 工具 | 动作 | 撤销靠什么 |
| --- | --- | --- |
| `create_doc` | 新建文档 | `beforeState.kind=create` → 撤销即放进回收站 |
| `create_module` | 新建模块 | 同上 |
| `append_blocks` | 末尾追加 | `snapshotMarkdown` 重放 |
| `update_doc` | **改写整篇正文**（可顺带改标题） | 快照重放 + `beforeState` 还原标题 |
| `rename_doc` | **改名 / 移动分类** | `beforeState` 还原标题与父级 |
| `delete_doc` | **放进回收站**（可恢复） | `beforeState` + `restoreDoc` 捞回整棵子树 |

## 三、守住底线的四条

放开不等于放任。下面四条是**不随"全自动"放宽**的：

### 底线 1：改写可以删减，但必须能原样撤回

> **这一条改过一次，是整份策略里改动最大的一处。**

**曾经的规则**：`update_doc` 逐块检查，任何既有文字在新内容里找不到就
**整次拒绝**。理由是"模型最常见的失败模式是顺手精简，用户写下的东西会悄悄消失"。

**为什么放开**：用户的原话是「**原文可以删，或者说是覆盖**」。
那道守卫在实践里挡掉的更多是**正当的整理** —— 删过时段落、合并重复文档、
把啰嗦的表述改短、纠正一段说反了的因果。它把 AI 变成了一个
"只能加不能减"的助手，而减恰恰是整理的一半。

**放开之后靠什么保证安全**：不是"不许删"，而是"**删了能原样退回**"。
本轮为此补了一条**复原通道**（这是放开的前提，不是附带功能）：

| 环节 | 落地 |
| --- | --- |
| 动手前存整篇快照 | `tool_call.snapshot_markdown` |
| 快照对应的**原块 id** | `before_state.originalBlockIds` |
| 撤销时按原 id **复活被删的块** | `repo.saveDocBlocks(..., { reviveIds })` |

⚠️ **第三条是关键，也是最容易漏的。** 块被改写删掉时会被软删
（最新 revision 的文本被清空、`seq = -1`），而 `saveDocBlocks` 的身份认领
**只看得见活着的块**（`seq >= 0`）。所以在复原通道存在之前，撤销能做到的只是
"把内容写回去，块拿到新 id"：

- 内容看着一模一样；
- 但 `@` 引用指向的旧 id **永远解析不到东西**；
- `cacheKey` 也随之变化，引用这篇文档的会话缓存回不到原状。

**这两个差别在界面上完全看不出来** —— 用户只会发现某个会话里挂载的块
莫名其妙变空了，而且不知道该怪谁。复原通道就是为这个洞补的：
它逐个校验"这个 id 是否真的被软删过、且内容与类型逐字一致"，
满足才按原 id 复活，否则交给正常的新建路径。

**代价（明确写出来）**：撤销从"可选的补救"变成了"**必要动作**"。
AI 现在可以真的弄丢内容，唯一的退回路径是撤销。所以：

- 用户必须知道撤销在哪、怎么用（见第五节）；
- 撤销的语义边界必须写清（见第四节：**你自己在 AI 之后做的改动会被一起丢掉**）。

### 底线 2：含子文档的模块不许被删

`delete_doc` 对**有子文档的模块**直接返回 `isError` 并说明原因，
要求模型先把子文档逐篇处理掉。

这不是技术限制（软删能整棵恢复），是**影响面**的取舍：
一次 tool call 带走十几篇文档，用户看到的是"一个模块空了"，
而他要逐个确认"哪些是本来就该删的"。

要求逐篇处理，等于把"一次大误操作"拆成"若干次可核对的小操作" ——
每次它都得说出删的是哪一篇。

> 用户明确要求保留这条（"保护模块是要留的"）。

### 底线 3：不能移动到自己子树里

`rename_doc` 会拒绝"把模块移进它自己的子孙里"。
那会让整棵子树从文档树上**消失**（根节点在自己的子树里，遍历永远走不到），
而用户只会看到"文档不见了"。

### 底线 4：AI 写的每一笔都要落审计

每次工具执行记一条 `tool_call`：哪个会话、哪个模型、第几轮、哪个工具、
原始参数串、成败、结果摘要、动到的文档、**动手前的快照**。
失败也记 —— 只记成功的日志会让人以为"没记录就是没执行过"。

**不动的红线**：AI 不能改 L0 人设 / L1 工作区约定。
那是每轮固定前缀，被改坏会污染之后所有对话；要改由人改。

## 四、撤销的语义边界（必须对用户说清）

撤销材料有两份，对应两类改动：

| 材料 | 管什么 | 哪些工具 |
| --- | --- | --- |
| `snapshot_markdown` | **内容**：动手前的整篇正文 | `append_blocks` / `update_doc` |
| `before_state` | **元数据**：标题 / 父级 / 删除标记 | `create_*` / `update_doc` / `rename_doc` / `delete_doc` |

撤销 = **把文档恢复成 AI 动手之前的样子**（快照重放 + 元数据写回），
不是"精准地撤掉 AI 加的那几块"。

所以：**如果 AI 写入之后你自己又改了这篇文档，点撤销会一并丢掉你的改动。**

这不是实现缺陷，是方案取舍：反向操作（"删掉刚追加的 N 块"）在用户中途
编辑过之后无法可靠地判断"哪些是 AI 加的"，反而会**悄悄吃掉**用户的内容。
两害相权，取行为可预期的那一个 —— 但界面上的确认框必须把这句话写明。

**撤销本身也可撤销**：新建类的撤销是"放进回收站"而不是彻底清除，
一次误点不会永久少一篇。

## 五、给用户的可见性（不是权限，但同等重要）

- 对话里出现工具活动条：运行中显示工具名与转圈，完成后显示结果摘要，失败标红；
- AI 新建的文档带 `sparkles` 图标，一眼能认出是 AI 建的；
- `GET /api/tool-calls` 能列出最近的工具调用，`POST /api/tool-calls` 撤销其中任一笔。

判据：**用户不看对话历史，也能在库里认出哪些内容是 AI 加的。**

## 六、这份策略怎么被验证

- **工具都在**：`tools.test.ts` 断言 `update_doc` / `rename_doc` / `delete_doc` 在清单里；
- **可撤销材料齐备**：`tools.test.ts` 遍历所有 `writes: true` 的工具，
  断言每一个都登记在"内容类"或"元数据类"里 ——
  一个两者都不是的写入工具 = 改坏了退不回去，那是真正不可接受的；
- **描述与策略一致**：`tools.test.ts` 断言 `update_doc` 的描述里
  **明确允许删减/覆盖**，且**不留旧守卫的措辞** ——
  描述还写着"必须原样保留否则被拒"的话，模型会因为怕被拒而不敢删，
  于是**功能放开了、行为没放开**；
- **删减真的能退回**（放开之后最要紧的一条）：`undo.test.ts` 断言
  删掉被 `@` 引用的块之后，撤销能把**内容 + 块 id + 引用解析**一起恢复。
  只断言"内容回来了"是不够的 —— 内容一样而 id 变了的话，
  `@` 引用永远解析不到东西，而界面上完全看不出来；
- **整篇覆盖也能退回**：同文件断言把正文换成完全不同的内容后，
  撤销仍逐字逐 id 复原；
- **模块保护真的挡得住**：`tools.test.ts` 断言含子文档的模块被拒，
  且**拒绝之后父子文档都原样还在**；
- **三种新工具各自可撤销**：`undo.test.ts` 分别验证
  改写（正文逐字 + 块 id + cacheKey + 标题）、改名移动（标题 + 父级）、
  删除（整棵子树从回收站捞回、父级不变）；
- **旧记录仍能撤销**：功能上线前的 `tool_call` 没有 `before_state`，
  它们全是内容类工具，走快照兜底路径（`undo.test.ts` 覆盖）。

**按 R6 验证过的**：把 `delete_doc` 的模块保护去掉，`tools.test.ts` 立刻变红；
把复原通道（`reviveIds`）关掉，`undo.test.ts` 里"撤销后块 id 与 `@` 引用一起回来"
那条立刻变红 —— 这一条尤其重要：**复原通道是放开改写之后唯一的安全网**，
它失效了整套放开就只剩"内容能救回来但引用断掉"，而那种失效在界面看不见。

> 丢内容守卫那条已经不是断言了（守卫本身被移除）。
> 它的旧实现 `findLostBlocks` / `describeLost` 仍留在 `tools.ts` 里 ——
> 一个被移除的安全机制应该留下可见的痕迹，让后人知道这里曾经有过什么、
> 以及为什么被拿掉，而不是无声消失。
